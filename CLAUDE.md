# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A realtime industrial sensor dashboard: 5,000 simulated sensors streaming at
10 Hz over WebSocket, plus 500,000 historical readings queried server-side.
Next.js 16 App Router, React 19, TypeScript strict, TanStack Query/Table/Virtual,
Recharts, Tailwind v4.

`README.md` documents the architecture and the measured performance results —
read it before changing anything in the data path.

## Commands

```bash
npm run dev        # simulator (:3101) + Next.js (:3000), shared lifecycle
npm run dev:next   # Next.js alone
npm run ws         # simulator alone
npm run build
npm run typecheck  # tsc --noEmit
npm run lint
npm test           # node:test
npm test -- --test-name-pattern "deadband"   # a single test
```

`npm run dev` goes through `scripts/dev.mjs`, which ties the two processes to
one lifecycle so Ctrl-C never leaves an orphan holding port 3101.

## Two runtimes, one codebase

`server/` runs on **plain Node 24** (native TypeScript execution), not through
the bundler. That has two consequences:

- Modules reachable from `server/` or `tests/` — which includes `src/lib/*` and
  `src/server/history-store.ts` — must use **relative imports with explicit
  `.ts` extensions**, not the `@/` alias, which only the bundler understands.
  `tsconfig.json` sets `allowImportingTsExtensions` for this.
- `package.json` is `"type": "module"`.

Client code under `src/app` and `src/features` uses `@/` normally.

## Next.js 16 specifics

Per `AGENTS.md` (regenerated by `next dev` — commit it rather than reverting
it), this Next.js version diverges from older training data. Read
`node_modules/next/dist/docs/` before writing Next-specific code.

- **`cacheComponents: true`.** Data fetching is dynamic by default; caching is
  opt-in via `"use cache"`. Do not reach for `unstable_cache`,
  `export const revalidate`, or a `runtime` export (unsupported here).
- Wrap `"use cache"` around a function returning **plain data**, never around a
  `Response` — a Response body is a stream and cannot be replayed from a cache.
  See `src/app/api/sensors/route.ts`.
- Typed route props (`LayoutProps<"/">`) are global and generated into `.next`;
  if they vanish, run a dev or build to regenerate rather than hand-writing them.

## TanStack Table v9 (not v8)

The installed major differs substantially from v8. Authoritative guidance ships
in the package: `node_modules/@tanstack/react-table/skills/`.

- `useTable(options, selector?)`, not `useReactTable`. The optional selector
  narrows what the owner re-renders for.
- Features are opt-in: `tableFeatures({ rowSortingFeature, ... })`. **An
  optional API does not exist until its feature is registered** — `size` /
  `getSize` need `columnSizingFeature`, `getVisibleCells` needs
  `columnVisibilityFeature`. A missing-property type error usually means a
  missing feature, not a wrong call.
- Render with `<table.FlexRender cell={cell} />`, not the `flexRender` function.
- Keep `features`, `columns` and the empty-data fallback at module scope. A
  fresh `?? []` or an inline `.map()` invalidates the row model every render.

## Invariants in the data path

Breaking any of these silently destroys the performance the project exists to
demonstrate. The **Transport & render metrics** panel is the fastest way to
confirm a change did no harm.

- **Live values never go into the table's `data`.** `data` is static sensor
  metadata; live values live in `SensorStore`'s typed arrays, and each mounted
  row subscribes via `useSensorRevision`. Putting a streaming value into row
  data rebuilds the row model on every frame.
- **A row renders its own cells.** `LiveRow` calls `row.getVisibleCells()`
  during its own render. Building cell elements in the parent and passing them
  down looks tidier but freezes the values: React skips re-rendering a child
  whose element reference is unchanged.
- **The virtualiser's scroll container needs a real height.** `flex-1` does not
  provide one on a normally scrolling page — the container grows to fit every
  row, every row counts as visible, and virtualisation is silently defeated.
  Watch "rows mounted" in the panel; it should be ~21, not 5,000.
- **Nothing allocates per sample.** Decoders hand primitives to a callback;
  sparklines reuse a per-component scratch buffer; the server reuses one frame
  buffer. 50,000 samples/second leaves no room for garbage.
- **The socket belongs to the effect instance that created it**, tracked in a
  local variable, not only in the shared ref. A closing socket's `onclose` must
  check identity before nulling the ref, or it orphans a newer connection that
  has already claimed it — the symptom is a throughput reading that climbs
  steadily while the server reports a normal rate.
- **Status transitions bypass the deadband.** An alarm is never withheld
  because the value only crept across its threshold (`server/simulator.ts`,
  covered by a test).

## Colour

Colours are defined **only** in `src/app/globals.css` and referenced as
`var(--chart-*)`, including from SVG attributes — there is deliberately no
palette copy in TypeScript.

The accent (indigo) was picked by measuring distance from the four reserved
status colours, because an accent that reads as "alarm" or "healthy" is a
usability defect in a monitoring UI. If you change it, measure first: amber and
aqua both fail (ΔE 8.1 from critical, 10.0 from good). Status roles are never
reused as series colours, and each is rendered with an icon *and* a text label
because the warning step is sub-3:1 on the light surface by design.

Numeric values carry the `.tabular` class, which switches to the mono face with
tabular figures so streaming digits do not change width.

## Hydration

Everything below the page header renders behind `useHydrated()`. Live values
move faster than hydration completes, so prerendering them guarantees a
mismatch. If you add a component that reads `SensorStore` or `MetricsStore`,
it must sit inside that gate.
